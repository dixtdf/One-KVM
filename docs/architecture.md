# 多通道平台架构与开发边界

状态：2026-10-28，实验分支 `codex/multi-channel-platform`。线上仍是
`0.2.8+custom.2` 和已经验证的手动 ID/密码前端。本文件描述目标架构；
只有明确标记“已实现”的内容才代表代码完成，不能据此声称多路已可部署。

## 目标与范围

沿用本仓库、GitHub Actions、固定上游源码和现有 ARM64 DEB 构建链。
复用 One-KVM 的采集、编码、OTG、串口 HID 和 RustDesk 协议实现；
新增通道模型、硬件发现绑定、工作进程管理、用户权限和多设备网页。
不从零重写硬件驱动或远程协议，不在本阶段开展 GPU 驱动工作。

通道是“一台受控电脑”的逻辑对象，拥有独立的持久 ID、视频资源、可选控制资源、
RustDesk ID/凭据引用、状态和会话。内部通道 ID 与用户手填的 RustDesk ID 分开。
允许只看画面的通道；此类通道必须拒绝所有控制事件。

不设置产品路数上限。配置数量和可同时运行数量是两回事；128 路模型测试不能证明
树莓派能运行128路。运行时按需启动并做内存、编码器和 USB 资源准入，资源不足报错，
不偷偷降低其他通道画质或替换数据源。

## 代码证据与改造原因

基线 `b5d13ee16e099df4082e1da96a37db0888c57bb7`：

- `src/state.rs` 的 AppState 持有全局 stream_manager、webrtc、hid。
- `src/runtime/builder.rs` 构造一套采集与控制并注入远程入口。
- `src/auth/user.rs` 的 single_user 明确拒绝多个账号。
- 当前 RustDesk 和网页共享全局视频/控制资源。

因此不能通过取消网页的路数限制完成隔离；全局资源替换可能导致画面与键鼠串路。

## 硬件身份与所有权

设备发现层只读枚举，普通用户不能传入任意宿主机路径。
登记资源后生成逻辑 ResourceId，并保存稳定选择器：

1. 可靠唯一身份，加设备型号和接口限定；原始硬件序列号不写公开日志或产物。
2. 身份不可靠时绑定物理端口及预期接口/型号，换端口需管理员重新绑定。
3. 内置 CSI、OTG 使用明确的系统设备身份。

`/dev/videoN`、`ttyUSBN`、USB bus/device 地址只作为当前解析结果，不作为持久主键。
身份缺失、匹配多个设备或型号不符时保持离线，绝不选择“第一个可用设备”。
同一物理接口的两个别名不能绕过独占检查。所有启动依赖先解析、检查，再交给工作进程；
后续租约必须原子获取，并在设备变化时重新核验，避免检查与使用间的竞态。

视频和控制默认由一个启用的通道独占；同一路多个观看者订阅同一编码流。
一条 Type-C OTG 物理链路不能凭软件变成连接多台电脑的多个独立 USB 设备。
第二台电脑需要独立的控制器/链路；现有 CH340 只证明串口存在，CH9329端仍需实机确认。

Unraid 的 USB 直通恢复属于宿主机适配器，不能靠树莓派 udev 别名解决。
该适配器只能操作管理员绑定的那个虚拟机和设备，不能批量重新附加所有 USB。

## 授权边界

全局管理员负责用户、资源登记、授权和通道创建。通道管理员可以配置获分配的通道，
不能创建用户或扩大自己的授权。通道权限为查看、控制、配置，默认拒绝。
每个 HTTP 请求、视频订阅、WebRTC 数据通道及 RustDesk 输入都按目标通道验证，
不能只隐藏菜单。撤权后阻断已有连接并释放按键、控制权，不能等待重新登录。

同通道可多人观看；输入需持有可撤销的控制租约。切换通道、断线、超时必须释放按键，
避免粘键。租约与鉴权都在后端执行，协议不能绕过。

RustDesk 账号体系与网页账户分开。第一版每通道独立 RustDesk ID 和密码，认证成功
只授予该通道能力；不得暴露其他通道为可切换显示器。网页授权不等同于 RustDesk 撤权。
共享密码无法区分个人，第一版不会声称实现了 RustDesk 个人账号级撤权；需要时另立
认证协议与客户端兼容决策。修改通道密码必须使旧连接/凭据失效。
秘密只留目标机，日志、API普通响应和公开构建中不出现明文。

## 运行结构

一个管理服务拥有账号、授权、资源租约和设备目录；每通道独立工作单元拥有视频、
控制和 RustDesk 状态。优先用受监管的独立工作进程隔离故障，进程只得到本通道资源。
启动某路、修改密码或编码设置，不重新初始化其他路 OTG。
管理面/工作进程 IPC 必须有本机身份校验，不能信任客户端提供的 user_id。

复用旧二进制的多进程仅能作为过渡，必须处理数据库目录、监听端口、OTG全局初始化、
旧API授权与进程退出释放，不能简单启动多个进程后称为隔离完成。

## 渐进迁移与验收顺序

1. **已实现但未接入运行时**：`platform-core` 的通道/资源模型、稳定匹配、物理接口
   冲突检查及按通道授权判定。无硬件I/O、数据库迁移、网络服务或线上配置修改。
2. 管理数据库、受限硬件发现、仅管理员的通道 CRUD，旧配置显式导入为一个通道。
   迁移需 SQLite backup、schema版本、事务及回退；现有账号、ID、Key、密码保持。
3. 工作进程/租约、单路兼容适配，现有 Mac 路先独立通过，再接第二路USB采集/HID。
4. 网页多设备、用户分配、WebRTC和键鼠全路径鉴权，跨通道攻击与撤权测试。
5. 每通道 RustDesk 认证/中继/输入隔离及硬件验收，再考虑部署替换稳定版。

第一阶段域模型测试不证明第2至5阶段已实现。没有通过两台实体电脑的视频和输入
归属测试、权限负例、重插恢复及旧版本回退前，不部署替换线上实例。

必须保留现有 C792桥接、systemd配置和Type-C OTG；不恢复已移除的Mac50Hz软件锁，
不重启Mac/Unraid来执行构建，也不把USB设备重新编号误报为采集与控制器驱动冲突。

## 测试分层

- CI域模型：重复身份、离线不回退、重枚举、独占与别名冲突、默认拒绝、撤权判定。
- 集成：持久化、迁移回退、每个API/数据通道权限、租约竞争、热插拔和进程故障。
- 协议：RustDesk错误密码/正确密码、直连/强制中继、加密回归、通道身份与输入归属。
- 实机：两路画面与键鼠对应、并发负载、断线释放、跨路重启影响和Unraid恢复。

构建通过只能证明对应检查通过，不能替代USB输入、编码资源或长期稳定性证据。
