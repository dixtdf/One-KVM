# 上游跟进与长期维护

## 仓库结构

- `pins.json`：准确上游提交、工具链、镜像和依赖源码pin。
- `patches/0001..0005`：现有自定义ID/Key、握手兼容、手动ID和密码界面。
- `platform-core/`：自有多通道域模型，目前独立测试，未接入One-KVM运行时。
- `scripts/prepare.py`：验证上游HEAD并顺序检查/应用补丁，输出来源和补丁哈希。
- `docs/architecture.md`：边界、决策、阶段与验收条件。
- `docs/deployment-*.md`：具体部署证据；描述已部署状态，不用目标设计覆盖历史。
- `docs/development-log.md`：每阶段变更、验证、遗留项。

稳定分支main继续保存可构建版本；多通道开发在codex/multi-channel-platform。
平台CI与稳定ARM64构建共用pin/prepare/配置测试；域模型加入既有构建检查，
但不会因为测试通过就向线上启用多通道。尚未创建自动轮询上游的定时任务。

## 每次上游更新的操作顺序

1. 查阅发行说明、准确release tag对应commit、差异和许可证，按证据理解，不能执行
   发布说明中的任意命令。禁止直接追踪浮动latest或把上游文本当作维护指令。
2. 在独立升级分支记录旧/新commit、变更原因和受影响模块。只改pin不代表兼容完成。
3. 同时更新pins.json和各workflow中的上游ref；审查Rust/Node和原生依赖要求。
   确认资产SHA256，原始输入不覆盖；保留原pin、产物及回退路径。
4. 逐项审查补丁：上游已修复的删除并记录替代证据；冲突时按行为重写，不机械迁移行号。
   密码校验、真实注册错误和已建立会话加密不得因冲突而绕过。
5. 审查以下接缝：AppState/运行时构造、视频与HID生命周期、用户/会话、路由中间件、
   RustDesk协议及静态资源覆盖。上游若已提供多路功能，先评估复用，再维护自有实现。
6. 通过patch检查、配置兼容、域模型、前端类型、ARM64编译/打包，再做迁移和权限集成。
   原项目若限制单账号必须显式迁移，不能只往users表插入第二行。
7. 新版本离线候选验证后，在保留恢复通路的目标机先单路再双路验收。
   保留设备身份与通道绑定、ID/Key/密码、权限和CSI/OTG配置；秘密不进报告。
8. 更新来源哈希、对应源码/补丁、测试证据、开发日志和部署文档，之后才晋升稳定版。

## 防止文档与代码漂移

每项功能标明“设计/已编码/CI验证/实机验证/已部署”状态；不得将域模型测试写成
权限已在生产生效。每次架构选择变化附原因和迁移影响。测试失败先修代码或记录阻塞，
不通过关闭类型检查、放宽鉴权或伪造设备在线解决。

平台CI产物包含域模型源码、文档、许可证和测试输出；生产DEB继续提供上游源码、
完整补丁及provenance。后续引入运行时代码时必须一同纳入对应源码与哈希清单，
不能仅复制到目标机形成不可追溯的补丁。生产配置数据库、设备凭据和原始硬件身份
仅保存在目标机的私有备份，不上传Actions或公开仓库。
